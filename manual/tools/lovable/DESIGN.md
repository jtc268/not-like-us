# Lovable design guide

Lovable can produce several design directions and lets a project bring its own design system. Use those controls before accepting the first polished page.

## Common defaults to reject

- **Generic SaaS shell.** A centered headline, two buttons, feature tiles, rounded sections, and a final CTA can appear before the product's information architecture is known.
- **Purple or blue-purple brand invention.** Do not let a prompt with no color direction become a purple product.
- **Placeholder-led layout.** Lovable notes that placeholders may be generic. Do not approve a layout whose balance depends on copy, metrics, or images that do not exist.
- **Dashboard autopilot.** Lovable says dashboards use its standard flow rather than the broader design-guidance flow. Inspect dashboard density, navigation, empty states, and data hierarchy closely.
- **One-shot convergence.** The first coherent preview is a proposal, not the visual system.

## Better moves

- Give Lovable the actual brand tokens, component rules, reference screenshots, and forbidden patterns before asking for pages.
- Request three structurally different directions. Compare hierarchy and workflow, not color swaps.
- Replace placeholder copy and fake data before judging the interface.
- For dashboards, specify the frequent decision, the dangerous action, scan order, table density, and narrow-screen behavior.
- Turn the selected direction into reusable tokens and components, then remove one-off styling.

## Prompt addition

```text
Before coding, propose three different information architectures using the real content.
Do not vary only the palette. Do not infer a purple SaaS brand, rounded card grid, or centered hero.
Use the supplied design system. Show loading, empty, error, long-content, and narrow-screen states.
```
